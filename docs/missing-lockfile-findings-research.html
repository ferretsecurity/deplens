Repository-wide findings

From manifest detection to project policy

How deplens can identify projects that declare dependencies without a lockfile—without painting itself into a corner before Docker image and GitHub Actions pinning checks arrive.

Go CLI 185 embedded rules reviewed 5 starter findings Monorepo-aware No runtime network
Recommendation

Add a second, repository-level evaluation phase over an indexed scan result. Keep findings as a first-class output type, separate from manifests and parser warnings. Define finding rules in the existing YAML list through typed operators—beginning with missing-companion—and give ecosystems a small, explicit project-scope resolver. This is the smallest design that handles absence, monorepos, future syntax findings, and platform ingestion cleanly.

Executive summary

The requested feature is not another file detector. Existing detectors answer “what is this file?” while missing-lockfile logic asks “given all files in this project, is an expected file absent?” That difference matters: absence can only be concluded after inventory is complete, and “this project” may be a directory, an ancestor workspace, or a package-manager root.

The current analyzer walks once, lets the first matching rule claim each file, and produces only ManifestMatch records. Its Warnings are parser diagnostics such as unreadable includes—not policy violations. Reusing either manifests or warnings for findings would make the CLI output and future platform API ambiguous.

01 Inventory Collect every non-ignored path and lightweight metadata.
02 Detect Run existing manifest parsers and emit reusable observations.
03 Resolve scope Group manifests and lockfiles into package-manager projects.
04 Evaluate Run finding rules and render deterministic CLI/platform output.
Most important correctness constraint

Do not equate “no lockfile in the manifest directory” with “no lockfile.” Yarn workspaces deliberately use a single root lockfile, and Cargo creates one lockfile for a package or workspace. A same-directory-only implementation will be noisy in exactly the repositories deplens is designed to scan.

Recommended first-release behavior

  • Scan and report findings by default in both human and JSON output.
  • Keep exit code 0 when findings exist; reserve policy gating for a later explicit --fail-on option.
  • Emit one finding per affected project anchor, not one per dependency or missing filename candidate.
  • Use stable rule IDs and stable fingerprints from the first release.
  • Only fire when a manifest conclusively declares dependencies; an empty manifest is not a violation.
  • Make output deterministic: sort by location path, then rule ID.

What exists today

The repository is well-positioned for this work, but the extension point must move up one level. The current implementation is intentionally file-local and manifest-oriented.

Area Current behavior Implication
Scan Walks files and appends ManifestMatch; there is no complete file index. Files irrelevant to manifest extraction are forgotten, so absence and sibling checks have no evaluation context.
Rule engine Each rule requires a filename regex and/or path glob; the first rule that claims a file wins. A repository relationship cannot be represented naturally as another parser key.
Default YAML 185 rules describe selectors plus at most one file parser. The same YAML can remain the source of truth if finding rules compile into a separate rule collection.
Output Human and JSON render a root plus manifests. Warnings belong to a manifest. Add a top-level findings collection; do not overload parser warnings.
Custom rules --rules replaces the embedded ruleset rather than merging it. A custom file must be able to contain both detector and finding rules, with validation for unresolved manifest types.
Runtime Self-contained static analysis with no network requests. Keep all finding evaluation local; documentation links are metadata, never fetched during a scan.

Useful existing capability

Four of the five proposed subjects already determine whether dependencies are present: JavaScript package.json, Pipenv Pipfile, Composer composer.json, and Cargo Cargo.toml. Ruby Gemfile is currently selector-only and needs a small detector upgrade before a missing-lockfile rule can avoid firing on an empty or comment-only file.

Terminology boundary

A manifest remains a recognized dependency-related artifact. A finding is a rule violation derived from one or more artifacts or observations. A diagnostic is an analysis problem such as malformed input. These should stay distinct in Go types, YAML validation, human output, and JSON.

Five rules to start with

These are intentionally manager-specific rather than a single “language has no lockfile” rule. A language may have several incompatible lockfile ecosystems; remediation and project boundaries belong to the package manager, even when rule IDs retain a language prefix for discoverability.

01
python-pipenv-lockfile-missing

Pipenv project declares packages without Pipfile.lock

Fire when the existing python-pipfile detector confirms at least one package category and no Pipfile.lock exists in the same project directory. Pipenv’s documentation says both files should be committed and that the lock records exact versions and hashes. This is the narrowest rule and the best implementation spike.

Do not fire for a metadata-only Pipfile or when Pipfile.lock is present but empty; stale/invalid lock content is a separate future finding.

02
ruby-bundler-lockfile-missing

Bundler project declares gems without Gemfile.lock

Fire when a Gemfile contains at least one effective gem declaration and the bundle root has no Gemfile.lock. Current Bundler guidance recommends checking the lockfile into version control for applications and gems.

Prerequisite
Upgrade Level 1 detector
False-positive risk
Low after parsing
Remediation
bundle install

Parser note: avoid a naive regex over every line. At minimum ignore comments and recognize common evaluated forms such as eval_gemfile; otherwise mark dependency presence unknown and skip the finding.

03
js-package-lockfile-missing

Node project declares packages without a covering lockfile

Fire when package.json has a non-empty dependency section and its resolved Node project has none of package-lock.json, npm-shrinkwrap.json, yarn.lock, pnpm-lock.yaml, bun.lock, or bun.lockb. Use the packageManager field and workspace markers as evidence, but accept any recognized Node lockfile in the first release.

Prerequisite
Level 2 exists
False-positive risk
Low with workspace scope
Remediation
Run selected manager install

A workspace member is covered by the workspace root lockfile. A nested package.json that is not selected by an ancestor workspace definition remains an independent project and needs a local lockfile. Ignore hidden npm lockfiles beneath node_modules; the directory is already ignored and npm documents those as an installation optimization, not a source lockfile.

04
rust-cargo-lockfile-missing

Cargo application or workspace has no Cargo.lock

Fire for a virtual workspace with dependencies, or a package that declares dependencies and is application-like (for example [[bin]] or src/main.rs), when the resolved Cargo root has no Cargo.lock. The Cargo guide now says to check a lockfile into version control when in doubt, but narrowing the first default rule avoids surprising library maintainers with historically different conventions.

Prerequisite
Level 2 + project kind
False-positive risk
Medium
Remediation
cargo generate-lockfile

A workspace member is covered only by the workspace-root Cargo.lock. A nested package excluded from the workspace is independent. A broader “Cargo library missing lockfile” rule can later be opt-in or informational.

05
php-composer-project-lockfile-missing

Composer application declares packages without composer.lock

Fire when composer.json has effective package requirements, no sibling composer.lock, and the package is application-like. Conservative evidence is type: project or an unnamed root package; allow rule configuration to override project kind because real application manifests are inconsistent.

Prerequisite
Level 2 + project kind
False-positive risk
Medium without classification
Remediation
composer update

Composer explicitly says projects should commit the lockfile while libraries need not. Therefore a broad rule over every composer.json should not be a default warning. Also exclude a require map containing only the PHP runtime or extension platform constraints if the product definition requires a third-party package dependency.

Fundamentally different approaches

A. Synthesize a manifest or warning

Fastest · reject

Add missing-lockfile logic to each manifest parser and attach a warning, or create a fake manifest entry representing the absent lockfile. This requires little output plumbing.

Advantages

  • Small code diff.
  • Existing renderers show something immediately.

Problems

  • Parsers cannot safely know the complete repository state.
  • “Missing” is not a manifest and policy violations are not parser diagnostics.
  • Docker and Actions checks would force unrelated semantics into manifest records.

B. Imperative checker registry in Go

Pragmatic · limited

After scanning, call hardcoded checker implementations such as CheckMissingNodeLockfile. YAML can enable check IDs and provide metadata, but the rule logic remains Go code.

Advantages

  • Typed, debuggable, and easy to optimize.
  • Ecosystem-specific workspace behavior is straightforward.
  • No embedded policy-language dependency.

Problems

  • YAML is mostly a registry rather than a rule definition.
  • Every variant requires Go changes.
  • Custom rules cannot express new relationships.

C. Typed finding operators over a repository index

Balanced · recommend

Compile existing file rules and new finding rules into separate internal collections. Scan once into an index, then run typed operators such as missing-companion, value-matches, and later reference-not-pinned. Operators are implemented in Go; their inputs, metadata, and composition are YAML-driven.

Advantages

  • Clear lifecycle for absence and cross-file checks.
  • Natural YAML integration with load-time validation.
  • Preserves a small self-contained binary and current parser investment.
  • Provides an incremental path to reusable observations and richer policies.

Costs

  • Requires new index, scope, finding, and rendering types.
  • Each genuinely new semantic family still needs one operator implementation.
  • The operator vocabulary must be kept coherent and documented.

D. General-purpose policy engine

Powerful · defer

Convert the scan index to structured data and evaluate Rego through embedded Open Policy Agent, or use an expression engine such as CEL. OPA is designed to reason declaratively over structured data and can be embedded in Go.

Advantages

  • Arbitrary cross-file policy without adding Go operators.
  • Mature negation, sets, metadata, and testing concepts.
  • Useful if deplens becomes a general policy platform.

Problems

  • Introduces a second language, larger dependency surface, and harder diagnostics.
  • Does not itself solve project-boundary facts; good input modeling is still required.
  • Embedding policy text inside YAML is less natural than typed fields.
  • Premature for three known finding families.

Recommended architecture

1. Build a repository index during the existing walk

Preserve current lazy content loading for parser performance, but retain every non-ignored relative file path in a compact set. Add detected manifests to indexes by path and type. The minimal internal shape is enough: 

type RepositoryIndex struct {
    Root            string
    FilesByPath     map[string]FileInfo
    Manifests       []ManifestMatch
    ManifestsByType map[ManifestType][]int
    Observations    []Observation
}

type Observation struct {
    Kind     string            // e.g. "docker.from", "github-action.uses"
    Path     string
    Region   *Region
    Fields   map[string]string // normalized values for finding operators
}

Do not expose RepositoryIndex directly as the JSON API. It is an internal execution model and can evolve independently from platform output.

2. Split rule compilation by rule kind

Keep one top-level rules: sequence. Existing entries remain valid and require no migration. An entry containing finding: compiles to a findingRule and is exempt from the file-selector requirement. Reject entries that mix a file parser and a finding operator. 

rules:
  # Existing file detector; unchanged.
  - name: python-pipfile
    dependency-type: pypi
    filename-regex: '^Pipfile$'
    toml:
      table-queries: ['*']
      exclude-keys: [source, requires, scripts, pipenv]

  # New repository-level finding rule.
  - name: python-pipenv-lockfile-missing
    title: Pipenv lockfile is missing
    severity: warning
    description: Pipfile declares packages but Pipfile.lock is absent.
    remediation: Run `pipenv lock` and commit Pipfile.lock.
    references:
      - https://pipenv.pypa.io/en/stable/pipfile.html
    finding:
      missing-companion:
        subject:
          manifest-types: [python-pipfile]
          has-dependencies: true
        companion:
          manifest-types: [python-pipfile-lock]
        scope: same-project-directory

Referencing manifest types rather than duplicating filename patterns lets detection improve independently. Load-time validation should ensure all referenced types exist in the active ruleset, catching broken custom rules before scanning.

3. Make project scope explicit

missing-companion needs a scope resolver, not a generic ancestor search. Begin with three resolvers:

ScopeResolutionUsed by
same-project-directory Subject and companion share a directory. Pipenv, Bundler, Composer
node-project Resolve an explicit npm/Yarn/pnpm workspace member to its workspace root; otherwise use the manifest directory. JavaScript
cargo-project Resolve Cargo workspace membership and exclusions; otherwise use the package directory. Rust

Scope resolvers should return a stable project anchor and confidence. If membership cannot be resolved safely—for example, a dynamic or unsupported workspace expression—skip the finding and optionally emit a diagnostic. A false negative is preferable to a noisy default rule.

4. Introduce a separate finding contract

type Finding struct {
    RuleID           string            `json:"rule_id"`
    Title            string            `json:"title"`
    Severity         FindingSeverity   `json:"severity"`
    Message          string            `json:"message"`
    Location         Location          `json:"location"`
    RelatedLocations []RelatedLocation `json:"related_locations,omitempty"`
    Remediation      string            `json:"remediation,omitempty"`
    Fingerprint      string            `json:"fingerprint"`
}

type ScanResult struct {
    SchemaVersion int             `json:"schema_version"`
    Root          string          `json:"root"`
    Manifests     []ManifestMatch `json:"manifests"`
    Findings      []Finding       `json:"findings"`
}

Location should point to the manifest that makes the expectation relevant, because a missing file has no location. Related locations can point to a workspace root manifest or configuration that established scope. Keep rule_id opaque and stable; SARIF similarly treats stable rule IDs and locations as core result concepts. A future --format sarif adapter can map this model without forcing the main JSON format to become SARIF.

5. Derive stable fingerprints from semantics

Platforms will eventually need to correlate findings across scans. Compute a fingerprint from a versioned tuple such as v1 + rule_id + normalized project anchor. Do not include the rendered message, absolute scan root, severity, or line number; all can change without creating a logically new finding.

6. Keep parser diagnostics separate

Existing per-manifest warnings remain useful for partial analysis. In a later cleanup they can be promoted to top-level diagnostics, but this feature does not require that migration. The immediate invariant is simply: findings never appear in ManifestMatch.Warnings.

Compatibility choice

Adding findings is structurally additive, but strict downstream schemas may still reject new properties. Publish the JSON contract and schema_version before platforms depend on it. If existing integrations cannot tolerate a version field, add only findings now and schedule explicit versioning before platform ingestion.

Existence is only the first policy

Do not silently broaden the rule to “usable lockfile.” Follow-on rules should separately detect malformed lockfiles, stale manifest hashes, lockfile/manager mismatch, conflicting lockfiles, and lockfiles excluded from version control. Separate IDs give users precise suppression and give platforms stable remediation analytics.

Fit for future findings

The recommended architecture is not lockfile-specific. Its reusable boundary is the observation, not a universal expression language. Parsers emit normalized facts; typed finding operators decide whether those facts violate a rule.

Future checkDetector emitsFinding evaluatesLocation
Docker FROM uses latest docker.from observation with registry, image, tag/digest, stage, region Tag absent or equal to latest, subject to scratch/alias semantics Exact FROM instruction
GitHub Action is not SHA-pinned github-action.uses with owner, repo, ref, job/step, region External action ref is not a full commit SHA; local and Docker actions excluded Exact uses: scalar
Missing lockfile Manifest and project-scope facts Required companion role absent from resolved project Subject manifest 
# Illustrative future rule shapes—not part of the first implementation.
- name: docker-image-latest
  title: Container base image is not pinned
  severity: warning
  finding:
    observation-match:
      kind: docker.from
      where:
        tag: { any-of: ["", latest] }
        digest: { absent: true }

- name: github-action-not-sha-pinned
  title: GitHub Action is not pinned to a commit
  severity: warning
  finding:
    observation-match:
      kind: github-action.uses
      where:
        source: external
        ref: { not-regex: '^[0-9a-fA-F]{40}$' }

This approach keeps syntax extraction in dedicated parsers, where comments, aliases, YAML node types, line regions, and language grammar can be handled correctly. It avoids asking YAML rules to become an ad hoc parser or asking every detector to render user policy directly.

Implementation plan

  1. Define contracts first. Add Finding, location, severity, and fingerprint types; document JSON compatibility and exit-code behavior. Add renderer goldens with zero, one, and multiple findings.
  2. Refactor scanning into inventory then evaluation. Retain all candidate paths, preserve existing manifest ordering, and prove existing outputs are byte-for-byte unchanged when no finding rules exist.
  3. Extend YAML compilation. Add finding metadata and the typed missing-companion configuration. Validate mutually exclusive rule kinds, stable unique names, severity, scope, and manifest-type references.
  4. Ship the Pipenv vertical slice. Same-directory scope exercises absence, YAML, JSON, human output, fingerprints, custom rules, and tests without workspace ambiguity.
  5. Add Bundler and its manifest detector upgrade. Cover comments, no-dependency Gemfiles, effective declarations, and lock presence.
  6. Add Node project resolution. Test npm, Yarn, pnpm, Bun, root projects, explicit workspaces, nested independent projects, and multiple accepted lockfiles.
  7. Add Cargo and Composer applicability. Keep conservative project-kind conditions and document intentional false negatives.
  8. Prepare platform handoff. Freeze rule IDs, publish example payloads, define fingerprint ownership, and add schema fixtures for consumers.

Tests required per rule

  • Manifest with dependencies + missing lock → exactly one finding.
  • Manifest with dependencies + accepted lock → no finding.
  • Manifest without dependencies + missing lock → no finding.
  • Malformed/unknown manifest status → no finding plus expected diagnostic behavior.
  • Monorepo/workspace covered and uncovered cases where applicable.
  • Ignored directory does not influence scope.
  • Human and JSON golden output, deterministic order, stable fingerprint.
  • Custom rules file accepts the rule and rejects bad references/configuration.
Repository contribution requirements

Each new default finding needs a representative testdata example in addition to proper unit tests. The new finding feature and any new/updated detector must be documented in README.md. A PR should show concrete old and new CLI output for a project that was previously only listed as a manifest and is now also reported with a finding.

When to reconsider a policy engine

Revisit OPA/CEL only when users need to compose novel cross-observation logic that cannot be represented by a small typed operator vocabulary, or when centrally distributed organization policies become a product requirement. By then, the repository index and first-class finding model recommended here remain useful: they become the policy engine’s input and output adapters, so the present investment is not discarded.
