Phase 1 Feature Specification

Library-backed VERS constraint output for dependency ranges

Add optional VERS output to dependency JSON by deriving a canonical range string from existing dependency type and native constraint fields, while preserving current source-faithful output.

Status: proposed Audience: maintainers Scope: JSON output Compatibility: additive
Clean step Add vers as an optional field derived from native constraints.
Engine Use github.com/git-pkgs/vers behind a local adapter, not directly from parsers.
Policy Whitelist ecosystems and omit output when conversion is ambiguous or lossy.

Goals

  • Expose a complete VERS range string for supported dependency constraints.
  • Keep raw and constraint unchanged as source-faithful fields.
  • Centralize conversion in shared analyzer code rather than detector-specific parsers.
  • Use an existing VERS implementation for ecosystem-specific range semantics.
  • Make support incremental by whitelisting ecosystems and test cases.
Core rule: if conversion is not confidently correct, omit vers. Missing normalized output is better than a wrong normalized range.

JSON Contract

Add one optional field to Dependency. The field value is a complete VERS URI string, including the vers: scheme and VERS type. The value is not just the constraint body.

Go typeinternal/analyze/scan.go
type Dependency struct {
    Type           PackageType       `json:"type,omitempty"`
    Raw            string            `json:"raw"`
    Name           string            `json:"name,omitempty"`
    Version        string            `json:"version,omitempty"`
    Constraint     string            `json:"constraint,omitempty"`
    VERS           string            `json:"vers,omitempty"`
    Section        string            `json:"section,omitempty"`
    Source         string            `json:"source,omitempty"`
    Extras         map[string]string `json:"extras,omitempty"`
}

vers must not replace constraint. Consumers that need the original manifest syntax should continue using constraint. Consumers that need normalized range semantics can use vers when present.

Architecture

Detectors continue to extract source data only. For example, requirements.txt extraction sets raw, name, and constraint. The shared rule result post-processing layer applies dependency type and then derives VERS.

1. Detector Extracts dependency fields from source files.
2. Rule metadata Applies dependency-type such as pypi.
3. VERS adapter Converts supported native constraints through the library.
4. JSON output Emits vers only on successful conversion.
Shared normalizerproposed
func normalizeDependencies(dependencies []Dependency, dependencyType PackageType) {
    applyDependencyType(dependencies, dependencyType)
    applyVERS(dependencies)
}

The existing call to applyDependencyType in rule detection should become a call to normalizeDependencies. Individual parsers such as py_requirements.go should not import the VERS library.

Conversion Policy

Conversion is handled by a small local API. This keeps deplens in charge of public behavior while delegating range parsing to the library.

Public analyzer helperinternal/analyze/vers.go
func ConstraintToVERS(packageType PackageType, constraint string) (string, bool) {
    scheme, ok := versSchemeForPackageType(packageType)
    if !ok {
        return "", false
    }

    normalized, ok := normalizeNativeConstraintInput(packageType, constraint)
    if !ok {
        return "", false
    }

    r, err := vers.ParseNative(normalized, scheme)
    if err != nil {
        return "", false
    }

    out := vers.ToVersString(r, scheme)
    if !validGeneratedVERS(out, scheme) {
        return "", false
    }
    return out, true
}

Omission Rules

Omit vers when any of these conditions are true:

  • Dependency.Type is empty or not whitelisted.
  • Dependency.Constraint is empty.
  • The dependency has a resolved version but no source range.
  • The candidate value is a full dependency requirement rather than an isolated range expression.
  • The native constraint includes non-version semantics that are not separated yet.
  • The adapter or validation step returns an error.
Python requirements need particular care. A constraint such as [all]>=0.110; python_version >= '3.10' contains extras and an environment marker. Phase 1 should omit VERS for that dependency unless those pieces are parsed into separate fields first.
The VERS library should receive only the isolated version range, not the full requirement string. For example, pass >=0.110, not fastapi>=0.110. The library may accept full requirement-like strings and produce misleading output instead of returning an error.

Library Adapter

Use github.com/git-pkgs/vers through an internal adapter. The adapter is the only package that should import the dependency.

Dependency decision

Pin the dependency version in go.mod and raise this repository's go directive to 1.25.6. At the time this spec was written, github.com/git-pkgs/vers@v0.3.0 declares go 1.25.6. Raising the repo directive makes the minimum toolchain explicit instead of relying on implicit GOTOOLCHAIN=auto downloads.

Toolchain Policy

The implementation should update go.mod from go 1.25.0 to go 1.25.6. CI images, local development environments, and release build containers must provide Go 1.25.6 or newer. This avoids surprise toolchain downloads in network-restricted environments and gives developers using GOTOOLCHAIN=local a clear minimum-version error.

Adapter Responsibilities

  • Map PackageType values to library schemes.
  • Reject package types not explicitly enabled by deplens.
  • Perform safe input normalization, such as trimming whitespace.
  • Reject full requirement strings that still contain the package name.
  • Reject constraints that mix range syntax with markers, extras, source URLs, or paths.
  • Validate generated output before writing VERS.

Observed Library Behavior

A direct check against github.com/git-pkgs/vers@v0.3.0 showed that PyPI full requirement strings can parse successfully while producing invalid-for-our-purpose VERS values. This is why the adapter must validate inputs before calling ParseNative.

Input to ParseNative Actual library output Spec decision
fastapi>=0.110 vers:pypi/fastapi%3E%3D0.110 Reject before calling the library.
fastapi[all]>=0.110 vers:pypi/fastapi[all]%3E%3D0.110 Reject until extras are parsed separately.
fastapi[all]>=0.110; python_version >= "3.10" vers:pypi/fastapi[all]%3E%3D0.110;%20python_version%20%3E%3D%20"3.10" Reject until extras and markers are parsed separately.
==2.32.3 vers:pypi/%3D2.32.3 Allowed. The encoded equality comparator is accepted as library output.
>=0.110 vers:pypi/>=0.110 Allowed range-only input.

Scheme Mapping

cargo cargo enable Enable when Cargo manifest extraction emits native constraints.

maven maven enable Enable for bracket-style Maven ranges when Java extraction is added.

composer none confirmed defer Do not enable until the library has a compatible scheme or an explicit mapping is chosen.

Ecosystem Scope

Phase 1 may add the library once, but it should not imply support for every ecosystem in the dependency. Each package type must be enabled deliberately with fixtures and expected JSON output.

Lockfiles

Lockfile dependencies with resolved version values should generally remain unchanged. Do not synthesize VERS for exact lockfile versions unless the source file actually expresses a range.

Non-Goals

  • Do not add full PURL output in this phase.
  • Do not replace or reinterpret the existing constraint field.
  • Do not evaluate whether a resolved version satisfies a range.
  • Do not parse Python markers or extras into new structured fields.
  • Do not claim support for every ecosystem implemented by the library.
  • Do not change human-readable CLI output.

Acceptance Criteria

  1. Dependency JSON includes optional vers.
  2. go.mod raises the repository Go directive to 1.25.6.
  3. VERS conversion is implemented in shared analyzer code, not in individual detectors.
  4. The VERS library is imported only through a local adapter.
  5. Whitelisted ecosystems have explicit unit tests with exact expected VERS strings.
  6. Unsupported or mixed semantic constraints omit vers.
  7. Existing JSON consumers remain compatible because the new field is additive.
  8. README.md documents the new field with a concrete output example.

This document specifies the standalone Phase 1 VERS feature. It intentionally leaves full package URL generation and deeper dependency identity modeling out of scope.
