Dependency source terminology and data model

This specification replaces “manifest” as the project-wide umbrella, defines the dependency-source taxonomy, and requires one complete rename across rules, Go code, JSON, CLI text, tests, and documentation.

Status
Implemented
Migration
Single breaking change
Output contract
One unversioned JSON shape
Core requirement

deplens MUST describe every reported repository item as a dependency source. A source MUST have one structural form and one or more semantic roles. “Manifest” and “lockfile” remain valid source forms; neither may be used as the umbrella term.

1. Status and normative language

This document is the implementation specification for the terminology migration. The keywords MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are to be interpreted as described by RFC 2119 and RFC 8174 when written in uppercase.

The migration is intentionally atomic. After it lands, the repository MUST contain only the new rule shape, Go names, JSON keys, CLI wording, tests, and documentation. There is no transitional repository state or second output path.

No schema versioning: JSON output MUST NOT contain schema_version, and the CLI MUST NOT expose a JSON schema-version selector. The post-migration format is the sole format.

2. Scope

Included

  • Canonical terminology and definitions.
  • Source forms, source roles, analysis states, detector capabilities, relationship, scope, and diagnostics.
  • All 185 built-in rule definitions and custom-rule validation.
  • Go types, fields, interfaces, methods, local variables, filenames where appropriate, and tests.
  • JSON and human-readable output.
  • CLI help text and the flag that controls visibility of sources without dependency references.
  • README.md, ARCHITECTURE.md, DEPENDENCY_COVERAGE.md, docs/glossary.md, golden files, and test names/messages.

Not included

  • Adding new detectors or changing which repository files current detectors recognize.
  • Increasing extraction coverage solely to satisfy the new taxonomy.
  • Scanning non-file inputs such as build submissions or SBOMs. The vocabulary permits those sources later, but this migration remains file-based.
  • Inferring direct/transitive relationship or normalized scope when current analyzers lack enough evidence.

3. Canonical terminology

TermNormative definitionRequired usage
Dependency sourceA repository item from which the scanner can obtain evidence about third-party components or dependency behavior.The umbrella term in code, output, and documentation.
Source formThe structural kind of a dependency source, such as manifest, lockfile, build definition, or source code.Exactly one form per reported source.
Source roleA semantic function performed by a source: declaring, constraining, resolving, verifying, configuring, organizing a workspace, using, or evidencing components.One or more unique roles per source.
Package manifestA package or project metadata file that declares identity and/or direct requirements consumed by a packaging or dependency-management tool.Use only for genuine manifests such as package.json, pyproject.toml, and Cargo.toml.
Requirements fileA standalone list of install requirements without the broader identity metadata of a package manifest.Examples include requirements.txt and Ansible requirements.yml.
LockfileA tool-generated record of dependency resolution intended to reproduce selected versions, often including transitive and integrity data.Use only when file semantics satisfy this definition; a filename is not sufficient proof.
Constraint sourceA source that limits versions a resolver may choose without necessarily introducing a dependency.Examples include constraints files, version catalogs, and override data.
Integrity recordA source that records hashes, signatures, or equivalent verification data.go.sum is an integrity record, not a lockfile.
Workspace definitionA source that composes projects, packages, or modules into a shared workspace.Examples include go.work, Gradle settings, and pnpm-workspace.yaml.
Build definitionA source that describes how software is built and may name third-party build inputs.Examples include Dockerfile, CMakeLists.txt, and Bazel build files.
Automation definitionA workflow or CI/CD source that references executable third-party inputs.GitHub Actions workflows use this form.
Deployment definitionAn infrastructure or deployment source that references runtime components.Compose and similar deployment configuration use this form.
Dependency configurationA source that changes registries, resolution policy, installation layout, credentials, or dependency-tool behavior.Examples include .npmrc, .yarnrc.yml, and Cargo configuration.
Usage referenceA reference showing that a component is imported, loaded, invoked, or selected for use.Examples include HTML scripts, container images, actions, and recognized source-code constructs.
Vendored component evidenceEvidence that a component copy is already present in the repository.JavaScript name/version banners currently provide this evidence.
DetectorThe runtime unit that selects candidates and optionally delegates content analysis.Every detector has a stable detector ID, form, roles, selectors, and derived capabilities.
RuleThe YAML configuration that defines one detector.Use “rule” for configuration, not as a synonym for analyzer.
SelectorA path-based predicate used to identify candidate files before content inspection.Current selectors are filename regex and relative path glob.
CandidateA file whose path satisfies a detector’s selectors but whose content may not be recognized.A selector match is not an analyzer recognition.
AnalyzerContent-aware logic that recognizes a candidate, assesses dependency presence, and may extract dependency references.Reserve “parser” for syntax decoding inside an analyzer.
Dependency referenceA source-level reference to a third-party component with raw and optional normalized data.Use for the Go item type. Human and JSON collection wording may remain “dependencies.”
Package typeThe PURL/VERS package type or protocol such as npm, pypi, or maven.Expose as package_type, never bare type.
Source groupThe original grouping label from the source, such as develop or packages-dev.Keep separate from normalized scope.
RelationshipWhether a dependency is direct, transitive, or inconclusive relative to the scanned project.Populate only when established by the analyzer.
ScopeA normalized usage category such as runtime, development, test, build, or optional.Populate only when a source-native group can be mapped confidently.
DiagnosticA structured, non-fatal analysis message with severity, code, and message.Replaces untyped warning strings.

Forbidden umbrella and implementation terms

TermRuleReason
manifestMUST NOT be the umbrellaMany current sources are not package manifests.
manifest-likeMUST NOT be usedIt substitutes uncertainty for classification.
typeMUST NOT be exposed unqualifiedIt currently conflates detector ID and package type.
parserUse only for syntax parsingRecognition and extraction are semantic analysis.

4. Required data model

Processing sequence

Repository fileThe scanner visits a regular file.
SelectorA filename and/or path predicate creates a candidate.
AnalyzerOptional content logic recognizes and analyzes the candidate.
Source resultForm, roles, analysis state, diagnostics, and path are reported.
DependenciesZero or more dependency references carry normalized data.

Source forms

Every built-in and custom rule MUST declare exactly one of these values:

manifest · requirements · lockfile · constraint-file · checksum-file · version-catalog · workspace-definition · build-definition · automation-definition · deployment-definition · tool-config · source-code · markup · vendored-file · other

Source roles

Every rule MUST declare at least one unique role. Role order MUST be preserved in output.

declaration · constraint · resolution · integrity · configuration · workspace · usage · inventory

Analysis dimensions

DimensionValueMeaning
PresenceunknownThe detector recognized or selected the source but could not establish whether dependency references exist.
PresenceabsentAnalysis conclusively found no dependency references.
PresencepresentAnalysis established at least one dependency reference, whether or not it was extracted.
ExtractionunsupportedThe detector does not extract dependency references from this source.
ExtractioncompleteThe analyzer completed extraction for the supported content, including a conclusive zero-result extraction.
ExtractionpartialAt least one reference was extracted, but analysis established that the result is incomplete.
ExtractionfailedExtraction was attempted but failed; diagnostics explain the failure.

State invariants

  • A non-empty dependency list MUST imply presence: present.
  • presence: absent MUST have no dependency entries.
  • extraction: partial MUST have at least one dependency and at least one diagnostic.
  • extraction: failed MUST have at least one diagnostic.
  • A selector-only detector MUST produce presence: unknown and extraction: unsupported.
  • A presence-only analyzer MUST use extraction: unsupported with either present or absent.
  • A successful extractor that finds no references MUST produce presence: absent and extraction: complete.
  • An analyzer that does not recognize a candidate MUST emit no source result; detector evaluation continues in rule order.
  • A per-file read or analysis failure MUST emit a source result with presence: unknown, extraction: failed, and a diagnostic; scanning continues.

Valid state combinations

PresenceExtractionRequired interpretation
unknownunsupportedIdentified source; dependency presence is not assessed.
unknownfailedAnalysis failed before a presence conclusion; dependencies are empty and a diagnostic is required.
absentunsupportedPresence-only analysis conclusively found no references.
absentcompleteExtraction completed and found no references.
presentunsupportedPresence is confirmed, but extraction is not implemented.
presentcompleteExtraction completed and dependencies are non-empty.
presentpartialUsable dependencies are non-empty, incomplete, and accompanied by a diagnostic.

Every combination not listed above is invalid and MUST be rejected by tests or internal validation.

Reference enums

EnumAllowed valuesOmission rule
Relationshipdirect, transitive, inconclusiveOmit when the analyzer has no relationship evidence.
Dependency scoperuntime, development, test, build, optionalOmit when a source-native group cannot be mapped confidently.
Origin kindregistry, git, path, urlOmit when origin is not established.
Diagnostic severitywarning, errorRequired on every diagnostic.

Detector capabilities

The ordinal maturity levels MUST be removed. Documentation MUST list applicable capabilities instead:

select · recognize · assess-presence · extract · normalize · relate · locate

Capabilities MUST be derived from detector/analyzer implementation, not accepted as user-authored claims in rule YAML.

5. Rule schema

The YAML top-level key remains rules. Each rule MUST use this shape:

Required rule shape
rules:
  - id: go-mod
    package-type: golang
    form: manifest
    roles:
      - declaration
      - constraint
      - resolution
    filename-regex: '^go\.mod$'
    analyzer:
      type: go-mod

Fields and validation

FieldRequirementValidation
idRequiredNon-empty and unique within the ruleset. It becomes the detector ID in output.
package-typeOptionalPURL-compatible package type. Unknown values are preserved and the loader emits a log warning.
formRequiredExactly one value from the source-form enum.
rolesRequiredNon-empty, unique values from the source-role enum. Input order is preserved.
filename-regexConditionalAt least one selector is required. Regex applies to basename only.
path-globConditionalAt least one selector is required. Glob applies to normalized relative path.
analyzerOptionalIf present, requires one recognized type; remaining keys are type-specific configuration.
  • When both selectors are present, they retain AND semantics.
  • Rule order and first-recognized-detector-wins behavior remain unchanged.
  • Selector-only rules omit analyzer.
  • YAML decoding MUST reject unknown fields. Removed keys such as name, dependency-type, and top-level analyzer keys MUST fail rule loading.
  • All built-in rules MUST be migrated to id, package-type, form, roles, and nested analyzer in the same change.
Selector-only rule
- id: go-sum
  package-type: golang
  form: checksum-file
  roles: [integrity]
  filename-regex: '^go\.sum$'
Configured generic analyzer
- id: helm-chart
  form: manifest
  roles: [declaration]
  filename-regex: '^Chart\.yaml$'
  analyzer:
    type: yaml
    exists-any:
      - dependencies

Required types

type DependencyReference struct {
    PackageType       PackageType       `json:"package_type,omitempty"`
    Raw               string            `json:"raw"`
    Name              string            `json:"name,omitempty"`
    Version           string            `json:"version,omitempty"`
    VersionConstraint string            `json:"version_constraint,omitempty"`
    VERS              string            `json:"vers,omitempty"`
    SourceGroup       string            `json:"source_group,omitempty"`
    OriginKind        OriginKind        `json:"origin_kind,omitempty"`
    Relationship      Relationship      `json:"relationship,omitempty"`
    Scope             DependencyScope   `json:"scope,omitempty"`
    Attributes        map[string]string `json:"attributes,omitempty"`
}

type SourceAnalysis struct {
    Presence   DependencyPresence `json:"presence"`
    Extraction ExtractionState    `json:"extraction"`
}

type Diagnostic struct {
    Severity DiagnosticSeverity `json:"severity"`
    Code     string             `json:"code"`
    Message  string             `json:"message"`
}

type DependencySourceResult struct {
    Detector     DetectorID            `json:"detector"`
    Path         string                `json:"path"`
    Form         SourceForm            `json:"form"`
    Roles        []SourceRole          `json:"roles"`
    Analysis     SourceAnalysis        `json:"analysis"`
    Dependencies []DependencyReference `json:"dependencies,omitempty"`
    Diagnostics  []Diagnostic          `json:"diagnostics,omitempty"`
}

type ScanResult struct {
    Root    string                   `json:"root"`
    Sources []DependencySourceResult `json:"sources"`
}

Analyzer contract

Required semantic interface
type sourceAnalyzer interface {
    Analyze(path string, content []byte) (sourceAnalyzerResult, error)
}

type sourceAnalyzerResult struct {
    Recognized   bool
    Analysis     SourceAnalysis
    Dependencies []DependencyReference
    Diagnostics  []Diagnostic
}

A syntax decoder used by an analyzer MAY retain “parser” in its name. The semantic interface that recognizes dependency sources MUST use Analyze and analyzer terminology.

Version field: the Go field MUST remain Version and JSON MUST use version. ResolvedVersion and resolved_version MUST NOT be introduced. A selected version belongs in version; a declaration range or exact declaration specifier belongs in version_constraint.

Method and error behavior

  • Detector methods SHOULD return a result object rather than parallel tuples of detector, dependencies, state, warnings, and booleans.
  • Rule-load, root-stat, and directory-walk failures remain fatal errors.
  • Per-file read and analyzer failures become structured diagnostics on a source result and MUST NOT abort the scan.
  • Diagnostic codes MUST be stable, lowercase kebab-case identifiers. Messages MUST contain the source-specific detail and MUST NOT be used as machine identifiers.
  • Read or total-analysis failures use error severity. Incomplete but usable extraction uses warning severity.
  • Source results remain sorted by normalized path and then detector ID.
  • Dependency ordering remains deterministic and analyzer-specific.
  • All local variables, test names, failure messages, and comments MUST use the canonical vocabulary unless they explicitly test a real manifest form.

7. JSON contract

JSON output MUST use the following shape. Field order is not semantically significant, but struct order SHOULD remain stable for readable golden files.

Required JSON output
{
  "root": "/repo",
  "sources": [
    {
      "detector": "js-npm-lock",
      "path": "frontend/package-lock.json",
      "form": "lockfile",
      "roles": ["resolution", "integrity"],
      "analysis": {
        "presence": "present",
        "extraction": "complete"
      },
      "dependencies": [
        {
          "package_type": "npm",
          "raw": "react@18.3.1",
          "name": "react",
          "version": "18.3.1",
          "source_group": "dependencies",
          "relationship": "direct",
          "scope": "runtime"
        }
      ]
    }
  ]
}

Serialization requirements

  • root MUST be the absolute cleaned scan root.
  • sources MUST always be present and MUST serialize as [], not null, when no source is found.
  • detector, path, form, roles, and analysis are REQUIRED on every source.
  • roles MUST be non-empty and retain rule declaration order.
  • dependencies and diagnostics MUST be omitted when empty.
  • raw is REQUIRED on every dependency reference.
  • Optional normalized dependency fields MUST be omitted when not established.
  • Paths MUST be relative to root and normalized to forward slashes.
  • HTML escaping remains disabled so source values are represented faithfully.

Removed JSON keys

The following keys MUST NOT appear after migration:

manifests · source-level type · dependency-level type · has_dependencies · constraint · section · source · extras · warnings · schema_version · resolved_version

8. Human-readable output and CLI

Path-first output remains the default. The renderer MUST use dependency-source terminology and MUST include the source form in detail labels.

Old output
Found 4 manifests:
- 1 with extracted dependencies
- 1 confirmed empty
- 1 with dependencies present, not extracted
- 1 with dependency status unknown

go-service/go.sum [matched]
Required output
Found 4 dependency sources:
- 1 fully extracted
- 1 confirmed without dependency references
- 1 with references present, not extracted
- 1 identified only

go-service/go.sum [checksum file · identified only]

Status labels

PresenceExtractionHuman label
presentcomplete[FORM · N dependencies]
presentpartial[FORM · N dependencies · partial]
presentunsupported[FORM · references present, not extracted]
absentAny valid value[FORM · no dependency references]
unknownunsupported[FORM · identified only]
unknownfailed[FORM · analysis failed]
  • No manifests found. MUST become No dependency sources found.
  • The CLI description MUST become Scan a directory tree and report dependency sources.
  • --show-empty MUST be renamed to --show-without-dependencies.
  • The new flag description MUST be include sources confirmed without dependency references.
  • Detector IDs MAY be shown in a future verbose mode but MUST NOT clutter the default path-first output.
  • Diagnostics MUST render beneath the affected source as severity [code]: message.

9. Documentation requirements

  • docs/glossary.md MUST be replaced with the canonical terms and definitions in this specification.
  • README.md MUST introduce “dependency source” before discussing specific manifests and lockfiles.
  • The README JSON description and examples MUST exactly match the required JSON contract.
  • The README detector table MUST replace maturity levels with derived capability names.
  • ARCHITECTURE.md MUST describe candidate selection, analyzer recognition, source results, and dependency references.
  • DEPENDENCY_COVERAGE.md MUST replace “Dep Storage Type” with source form and source roles. Existing classifications MUST be reviewed, not mechanically relabeled.
  • References to genuine ecosystem manifests remain valid. Generic phrases such as “manifest details,” “all manifests,” and “manifest detector” MUST be rewritten.
  • The implementation PR MUST include concrete old/new CLI and JSON examples because behavior is user-visible.

10. Atomic migration procedure

These steps are implementation order within one change, not release stages. The repository MUST not be merged in a partially migrated state.

  1. Define enums and core structs. Add forms, roles, analysis states, relationship, scope, origin kind, diagnostics, dependency references, and dependency-source results.
  2. Replace the rule schema. Rename fields, nest analyzers, enable strict unknown-field validation, and classify every built-in rule.
  3. Rename analyzer contracts. Replace parser-oriented semantic names and return explicit recognition, presence, extraction, dependencies, and diagnostics.
  4. Replace scan aggregation. Emit ScanResult.Sources, initialize it as a non-nil empty slice, and preserve current traversal and ordering.
  5. Migrate every analyzer. Populate the required state combinations and rename dependency fields. Keep Version/version.
  6. Replace renderers and CLI wording. Implement the sole JSON contract, new human labels, and --show-without-dependencies.
  7. Rewrite tests and goldens. Remove old-output tests, add state-invariant tests, strict-rule-schema tests, and complete new golden files.
  8. Rewrite documentation. Update the glossary, README, architecture, coverage matrix, examples, and code comments.
  9. Run terminology audit. Search the repository for old generic identifiers and wording; retain “manifest” only where it names a real source form or historical old-output example.
  10. Verify behavior. Confirm that detected paths, detector IDs, raw dependency values, and warnings converted to diagnostics retain current scanner coverage.

11. Acceptance criteria

  • All 185 built-in rules load under the strict new schema and declare one form plus at least one role.
  • Removed custom-rule keys are rejected with actionable field errors.
  • go test ./... passes.
  • All modified Go files are formatted with gofmt.
  • JSON golden tests contain sources, required source metadata, explicit analysis state, and dependency version.
  • No JSON output contains schema_version, resolved_version, or any removed key.
  • Empty scan JSON emits "sources": [].
  • Human output says “dependency sources,” distinguishes identified-only from confirmed absence, and shows source form.
  • The CLI accepts --show-without-dependencies and rejects --show-empty.
  • Analyzer recognition behavior, rule ordering, traversal, ignored directories, matched paths, and extracted raw references remain unchanged.
  • Every partial or failed analysis result contains a structured diagnostic.
  • README contains concrete old/new output examples and matches implemented behavior.
  • docs/glossary.md is the canonical Markdown counterpart of this specification.
  • A repository-wide terminology search finds no generic manifest umbrella or old Go identifiers outside historical examples.
